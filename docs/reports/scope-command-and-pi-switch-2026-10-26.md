# 目录拒绝后命令暂停与外部 Pi 开关优化

## 本轮改动

用户确认慢开关是设置 → 常规的“在外部终端使用 Pi”。本轮没有新增行为提示词来承担目录访问限制，也没有新增工具、改名 SDK 工具或重做页面。

### 拒绝后换 Shell 的执行路径

- 范围检查用专门的 ProjectScopeAccessError 区分真正的目录越界与相对路径格式错误、文件不存在。只有前者触发暂停。
- 发生范围拒绝后，该请求后续的 project_command 在执行函数内直接拒绝；工具调用入口同时阻止 Shell 和继续委派／引导子代理。直接嵌套调用项目命令也不能跳过执行函数的检查。
- 允许范围内的文件读写和复制继续可用，不会因一个根被拒绝而封锁所有文件工具。
- 拒绝状态使用 SDK appendEntry 保存，保持现有会话格式。以真实用户消息 ID 确定请求边界；子代理创建与 RPC 重开都跟随父会话的用户请求 ID，自动通知、自动续轮、自动 resume 或重开子会话不能解除。
- 父会话进入新的用户请求后，可以在允许目录重新运行命令；不会因此新增关联目录或变更授权。

**准确边界：这修复的是“已经发生目录范围拒绝后，本次请求立即换命令继续”的路径，不是操作系统级目录隔离。**未发生拒绝时的任意 Shell 命令、已启动进程、手动终端和第三方工具不因此获得统一文件访问限制。新请求恢复命令能力也不意味着此前拒绝的路径已经获授权。没有用命令字符串扫描假装解决这个更大的问题。

本次采取保守暂停：拒绝之后，即使接下来某条命令本身合法，也会暂停到用户的新请求。这样不需要猜测命令正文是否在换方式访问。合法文件工具仍可继续。测试中主代理曾先选错仓库根，触发这一暂停；该现场已保留，没有隐去。

### 外部 Pi 开关

原保存路径同步等待 PowerShell 的 Add-Type 编译和 Windows 环境广播；广播还可能等待其他窗口，因此开关长时间处于等待状态。

- 注册表修改与系统广播分离：仍等待入口、用户 PATH、全局设置保存完成才返回成功，广播在后台执行。重复快速变化合并广播；无实际 PATH 变化不广播。
- PATH 状态读取合并并发查询，短缓存 3 秒；更改时失效，成功后更新，旧的异步查询不会覆盖新结果。启动入口修复同样使用这条逻辑。
- 界面点击后立即切换到目标状态，保存中阻止重复操作；保存失败恢复原状态并显示错误。
- 没有修改系统 PATH；原有无关 PATH 项、变量引用、值类型、独立 Pi 命令及应用内终端继续沿用原规则。

### 开关响应

- 优化前真实 GET 连续读取：666、446、437 毫秒。
- 优化后首次请求含开发服务重新编译开销，为 2557 毫秒，不作为优化收益；缓存窗口内后续真实读取为 15、13 毫秒。超过 3 秒仍会重新查询系统状态，不承诺所有首次读取都变为十几毫秒。
- 真实浏览器设置页面：拦截保存响应并保持未返回，开关约 76 毫秒已反馈目标状态；再模拟保存失败，恢复原状态，显示错误。两次操作仅发出两次保存请求，页面脚本错误为 0。
- 未在用户真实 PATH 上反复开关。保存路径测试使用独立目录与模拟系统调用：模拟环境广播一直不返回时，设置保存、状态查询已能完成；并发读取合并，保存刷新缓存，设置保存失败会恢复原入口状态。

这些测量分别验证界面反馈、状态读取和保存等待路径，不把模拟注册表测试冒充真实用户 PATH 写入耗时。
