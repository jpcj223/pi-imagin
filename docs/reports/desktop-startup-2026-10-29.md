# 安装版启动慢：检测与优化方案

日期：2026-10-29。用户确认入口为桌面／开始菜单的安装版。本轮仅诊断，没有修改产品代码、提交或推送，也没有调用模型。

用户随后授权修改，实施及验证结果见 [启动优化实施记录](desktop-startup-fix-2026-10-29.md)；下文保留诊断时的数据与限制。

## 结论

**后续录像补充：真实安装版启动明显比隔离测试慢。** 用户提供的 `20261029-0413-01.6668030.mp4` 全长 43.37 秒：第 4 秒已显示“正在启动本地工作区…”，到第 38 秒仍停留于此；第 39 秒变为“正在打开工作区…”，第 40 秒为“正在恢复工作区…”，第 41 秒主界面可见。启动页约停留 37 秒，主要约 35 秒在后台可连接前；页面打开／恢复约 2 秒。录制开头包含开始菜单操作，未将视频第 0 秒当作精确点击启动时刻；也没有把主界面出现当作已验证键盘输入成功。

因此，下文空配置约 7 秒仅是隔离测试数据，**不能代表用户实际启动耗时**。已有两项后台优化仍有依据，但不能声称它们足以解决录像里的约 35 秒等待。下一步必须优先补齐真实入口的后台阶段记录，定位相较隔离测试多出的约 30 秒。录像能定位阶段，不能独立区分 SDK、原配置、网络初始化或文件访问等具体原因。

已复现安装程序在空配置下仍需约 7 秒进入工作区。主要可定位开销在后台首次可连接之前，而非聊天内容或模型响应。当前两条后台加载链会提前载入 SDK，削弱已有的延迟预热设计：

1. Next 生产运行时默认预加载页面和接口，包括静态引用 SDK 的接口。
2. 桌面 instrumentation 立即导入 `pi-command`；它通过 `global-settings-file` 静态引用整个 SDK，并在启动时执行外部命令入口检查／修复。

隔离后台对照支持优先调整这两条链；但尚未测量实施后的完整可见窗口启动效果，不能承诺整体从 7 秒降至 1 秒。用户本次原配置的最新完整日志未找到，若实际等待远大于本次约 7 秒，仍需补采该入口的阶段日志。

## 实测结果

### 录像后的同配置再次启动（北京时间 12:46）

确认用户录像中的安装版进程已退出后，使用同一个安装程序及其现有默认浏览器数据／agent 配置，静默启动一次；未设置 `PI_OFFLINE`，未发送对话。约 **7.845 秒**观察到就绪，后台进程启动到健康检查通过约 **2.88 秒**，认证 27 毫秒，首页请求约 2.06 秒，会话目录最多约 204 毫秒。隐藏窗口绘制确认仍约 1.75 秒，因此不能把该项当作正常可见窗口的确切耗时。

诊断正常退出，并移除了仅供本次使用的两个 smoke 控制文件。启动前后核对默认 agent 目录中的 `settings.json`、`models.json`、`auth.json` 哈希一致；没有重置数据或修改产品代码。

**此次没有复现录像的约 35 秒后台等待。** 说明它不是本轮同环境下每次固定出现的延迟，但不足以证明只发生于更新后首次启动，更不足以认定杀毒、网络或编译缓存中的某一项是根因。

诊断曾尝试通过 `NODE_OPTIONS` 注入仅记录元数据的观察器；打包版 Electron 报告不支持该选项，实际未生成后台细分 trace。保留真实的阶段日志与该限制，没有把观察器视为已成功采样。此后预期位置的 `desktop.log` 记录了本次启动；录像那次缺失记录的原因仍未确定。

下一步若处理完整问题，首先给启动器增加可独立保存的诊断阶段记录，至少分开记录：Node 入口、Next 入口、instrumentation、首个健康请求、SDK 载入、外部命令检查和主界面就绪；需要覆盖实际慢启动。不能用本次较快的再次启动结果宣称 35 秒问题已经解决。

## 原因与代码依据

### 已确认：首屏前加载了本可延后的依赖

- 安装版 `server/server.js` 的 `experimental.preloadEntriesOnStart` 为 `true`。
- 安装版 Next `next-server.js:470` 启动预加载，`:515` 后遍历页面／接口入口。
- 例如 `app/api/models/route.ts:4` 在模块顶部直接导入 SDK。即使还未打开模型设置，也会因预加载执行模块加载。
- `instrumentation-node.ts:40` 在桌面启动时立即导入并初始化 `pi-command`。
- `lib/pi-command.ts:7` 导入全局设置模块；`lib/global-settings-file.ts:3` 从 SDK 导入 `getAgentDir`，因此简单目录查询带入 SDK。
- `lib/pi-command.ts:168` 初始化外部入口，检查／修复 PATH 时启动 PowerShell。
- `lib/sdk-preload.ts` 虽然等 `workspace-loaded` 再调用 `loadSdk`，上述入口仍可绕过该门槛。这属于依赖时机问题，无须修改 SDK 本身。

### 待补测

- 正常可见窗口中的绘制确认等待是否同样明显。
- 用户实际配置下的会话恢复、插件／MCP 初始化耗时。空配置目录接口很快，不能据此宣称大历史会话一定没影响。
- 更新后首次启动的文件扫描／安全软件开销。本轮没有对应系统证据，不列为已确认原因，也不建议关闭防护。
- 本轮在更新后的当天测量，不能证明新版相对旧版发生回归。

## 建议实施顺序

### 第一批：减少首屏前工作，优先实施

1. **仅桌面打包配置关闭全路由预加载**。普通网页部署保持原策略；首次使用的功能仍按需加载。验证首页、登录、健康接口及首次打开模型／设置／终端，防止把遗漏依赖留到用户点击时才暴露。
2. **拆掉轻量设置读取对 SDK 的静态依赖**。优先复用已有 `lib/agent-dir.ts`，它已经按 SDK 的目录规则实现，不必重新设计配置系统；核对环境变量、中文路径、文件 URL 等兼容性。
3. **外部 Pi 入口检查移至工作区就绪后执行**，并继续按需读取真实状态。更新后修复命令入口的能力、关闭状态和失败重试必须保留；已有初始化去重／串行机制能复用则复用。只延后初始化，不删功能。
4. **补齐安装版阶段日志**：记录构建标识、实际日志路径、后台启动、首次健康响应、页面布局、桌面确认；把首屏可用与模型运行时就绪分别记录。不能只凭 Next 的 `Ready in 0ms` 判断后台已可用。

这批预计半天到一天，包含定向检查与 Windows 安装包复测。上述后台实验约节省 2 秒，但完整应用收益必须以实际包复测为准；恢复已有对话时 SDK 可能仍是必要依赖。

### 第二批：根据第一批结果处理窗口等待

- 检查真实可见窗口的 ready 到 IPC 间隔，若仍明显，再修正双帧确认在隐藏／被遮挡状态下的等待机制。
- 仍需保留真实布局就绪、来源校验与有限超时；不提前宣告可交互，不以隐藏加载页掩盖后台未就绪。
- 预计约半天，是否需要实施由可见窗口数据决定。

暂不建议重做启动架构、常驻后台、删除历史数据或扩大预热范围。现有日志中的重复目录请求可以另行去重，但本次只耗约百毫秒，优先级低于上面的启动链。

## 实施后的必要验收

- 同一安装路径、同一机器，分别测更新后首次／再次启动；统一记录启动至窗口出现、首屏可用、恢复对话可用、模型首次可用。
- 空配置与原有配置各测；原配置需等用户正常退出安装版后复用，不复制或输出凭据。
- 覆盖无历史会话、恢复已有会话、外部 Pi 开关开／关、初始化失败后重试、退出无后台残留。
- 首次打开模型、终端及发送一条必要对话，确认没有只把全部延迟转移到第一次操作；对话检查需单独控制用量，本轮未执行。
- 只运行改动相关测试及类型／lint；不重复无关真实对话测试。
